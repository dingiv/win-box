# 05 已知问题：物理屏「网格状白色方块」

> 一句话：**IDD 干活（LG 窗口有动作）时，核显驱动的物理屏出现规则白色方块、画面破碎；
> LG 窗口本身完全干净。** 这是 AMD 驱动的 D3D12 传输内存/显存分配缺陷，配置层无法根治。

## 1. 现象

> **关于本文**：这是当时的**实录**（含走过的弯路与证据），不是使用说明。
> 命令已规整为本仓库的形式（`winbox …`）；接口以 `docs/interfaces/` 为准。

- 开机进登录界面起就可见；**LG 窗口有动作时更明显/闪烁**；
- 只在**物理屏**（核显的另一路扫描输出）上出现，**LG 窗口干净**；
- 形状是"网格状白色方块、随机分布" —— 网格粒度对应 D3D12 资源的分块（tile）粒度；
- 降物理屏分辨率 ✗、降 IDD 模式到 30Hz ✗、改拷贝模式仅改变严重程度 ✗。

## 2. 链路与两条传输路径

```
DWM 合成 → IDD 的虚拟显示器 → LGIdd.sys → 把帧搬进「共享传输内存」（IVSHMEM 128MB）
                                            ├─ direct：把共享内存当 D3D12 custom heap，GPU 直接写
                                            └─ indirect：GPU 在本地显存渲染 → CPU 回读 → 写共享内存
→ LGMP 帧队列 → 宿主客户端 → KVMFR DMA-BUF → NVIDIA 纹理
```

`LGIdd` 启动时会做一次 **HeapTest**（在传输内存里创建最小资源 + 拷一次）来决定能否走 direct。

## 3. 实测到的三条失败边界（每条都有日志）

| 配置 | 结果 | 日志证据 |
|---|---|---|
| `ForceIndirectCopy=0`（direct） | ❌ **GPU 直接挂起** | `CD3D12Device::HeapTest:209 \| Device Removed (0x887A0007 …GPU 不响应更多的命令)` 随后 `Unable to create resources in transport memory, falling back to indirect copy` |
| `ForceIndirectCopy=1` + `ForceFullDirectCopy=1` | ⚠️ 不挂，但每帧写全量 → 方块**更多** | `CHardwareFrameProcessor: Forcing full copies to direct transport memory` |
| `ForceIndirectCopy=1` + `ForceFullDirectCopy=0`（当前采用） | ⚠️ 不挂 + 只写脏区 → 方块**最少**但仍有 | `CD3D12Device::Init:75 \| Forcing indirect transport copies` + `Frame graph g=1 mode=hw` |

`0x887A0007 = DXGI_ERROR_DEVICE_REMOVED`（GPU 停止响应命令，TDR 级别）——
不是"功能不支持"，而是**驱动/引擎直接挂住**。

## 4. 机制分析

### 观察一（最重要）：LG 窗口干净

说明**共享内存里的帧数据是正确的**。如果任何一次拷贝把像素写错，LG 窗口就会花屏。
→ 传输的**数据面**没问题。

### 观察二：受害者是"另一路扫描输出"

客机地址空间里，传输内存和核显的显存窗口是**不同设备、不同地址**：

```
客机地址空间（HMP 实测）
0x387000000000 - 0x38700fffffff   iGPU BAR0（256MB，显存窗口）
0x387010000000 - 0x387017ffffff   IVSHMEM BAR2（128MB，IDD 的传输内存）
0x387018000000 - 0x3870181fffff   iGPU BAR2（2MB，寄存器块）
```

所以：**IDD 干活时，驱动/GPU 有一些写入落到了不属于它的显存区域**
（显示扫描输出或其它资源）→ 那块内存被污染 → 屏幕出现白方块。
"LG 有动作时更明显" ⇒ 每次帧更新都触发拷贝与资源创建/释放，踩中越界写的概率越高。

### 可能的机制（按可能性排序）

1. **显存分配器/边界管理缺陷（最可能）**
   IDD 的资源类型（共享堆资源、回读资源、大尺寸扫描缓冲）触发分配缺陷 →
   分配出的物理范围与显示扫描输出**重叠**，或拷贝超出资源边界。
   这能同时解释"数据正确但旁边显存被写坏"和"direct 路径直接挂 GPU"。
2. **共享内存的 GPU 映射错误**
   驱动无法为"高地址 BAR 背衬的内存"建立正确的 GPU 页表/DMA 映射 →
   GPU 写入落到错误目标（HeapTest 直接挂 = 访问非法映射）。
   社区里同代核显出现过的 `VFIO_MAP_DMA failed: Bad address`（5600G 案例）是同类问题的另一面。
3. **超高地址 BAR 的驱动处理缺陷**
   客机里核显与共享内存的 BAR 都在 ~62TB（`0x387…`）。
   某些驱动的 DMA/ATS 路径在超高地址上出错；BAR 地址由固件分配，配置层无法干预。

## 5. 已排除的配置层因素

| 变量 | 试验 | 结果 |
|---|---|---|
| 扫描输出大小 | 降物理屏分辨率 | 无效 ✗ |
| 帧率/写入量 | IDD 模式降 30Hz、客户端 `fpsMin=30` | 帧产率跟随主屏 60Hz 合成节奏，未降下来 ✗ |
| 拷贝模式 | direct / indirect × 全量 / 脏区 | 只改变严重程度 ✗ |
| 显存大小不匹配 | 宿主 amdgpu 报 `VRAM: 2048M`，客机 WMI 也报 2GB | **一致**，排除 ✗ |
| 驱动版本 | 回退过一版 | 仍 43/仍方块 ✗ |
| IDD 偏好 | 三个布尔值组合 | 只能规避"挂起"，不能修"越界写" ✗ |

**判据**：同一驱动 direct 直接挂 GPU、indirect 仍越界写 —— 这是驱动内部内存管理缺陷，
没有任何应用层开关能绕过。

## 6. 出路

| 路线 | 原理 | 代价 |
|---|---|---|
| **不插物理显示器**（推荐） | 没有活动扫描输出缓冲 ⇒ 没有东西可被写坏；IDD 路径照旧（渲染适配器仍是核显、画面干净） | 少一块物理屏（也正是本项目最初的目标：HDMI 不插显示器） |
| **换 LG 传统 Host 应用** | 它用 **DXGI Desktop Duplication（只读抓屏）+ CPU 拷贝**：不碰 D3D12 custom heap，也不创建 IDD 那类资源 ⇒ 绕开两处弱项 | 变成"镜像"形态；核显仍需一个活动输出（真显示器或 **HDMI 诱骗插头**） |
| **等/换更新的 AMD 驱动** | 需要 AMD 修 D3D12 自定义堆 + 显存分配器 | 不可控（当前已是最新一版） |
| **报 bug** | 证据链干净（见下） | 需要时间 |

## 7. 若报 bug，附这份证据（最有说服力）

```
1. CD3D12Device::HeapTest:209 | Device Removed (0x887A0007 …GPU 不响应命令)   ← direct 必挂
2. 同一会话 LG 窗口画面完全正常（传输数据正确）                              ← 数据没错
3. 物理屏同时出现规则白方块（有越界写落到扫描输出）                          ← 写到了不该写的地方
+ 环境：AMD 驱动 32.0.21045.11001（2026-09-25）
+       LG IDD B7-829-cdba29f2，IVSHMEM 128MB
+       客机 BAR: iGPU BAR0 0x387000000000 / IVSHMEM 0x387010000000
+       复现：IDD 生效 + 物理显示器接在核显 HDMI 上 + LG 窗口内有画面活动
+       完整日志：C:\ProgramData\Looking Glass (IDD)\looking-glass-idd.txt（+ .1~.4）
```

## 8. 当前采用的设置（`winbox lg --idd-show` 可查）

```
ExclusiveMonitor    = 0    不独占（允许物理屏共存）
ForceIndirectCopy   = 1    避免 GPU 挂起（必需）
ForceFullDirectCopy = 0    写入量最小
DefaultRefresh      = 60
ExtraMode           = 1600x900@60*
```
