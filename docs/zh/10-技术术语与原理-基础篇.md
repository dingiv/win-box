## 一、虚拟化基础：谁是谁

> **关于本文**：这是当时的**实录**（含走过的弯路与证据），不是使用说明。
> 命令已规整为本仓库的形式（`winbox …`）；接口以 `docs/interfaces/` 为准。

| 术语 | 一句话 | 在本项目里 |
|---|---|---|
| **KVM** | Linux 内核模块，提供硬件虚拟化（AMD-V/Intel VT-x）能力 | 宿主内核里 |
| **QEMU** | 用户态模拟器/虚拟机监视器，真正"跑"虚拟机的进程 | 我们 VM 的 `qemu-system-x86_64` 进程 |
| **libvirt** | 管理 QEMU/KVM 的守护进程 + 统一 XML 配置 + API | `virsh` / `virt-manager` 的后端 |
| **host / guest** | 宿主 / 客户机 | 宿主 Ubuntu，客户机 Win11 |
| **vCPU** | 虚拟 CPU 核 | 我们给 8 个（`1×8×1` 拓扑） |
| **qcow2** | QEMU 的写时复制磁盘镜像格式，支持快照/backing file | 客机磁盘；快照 `clean-system`、`gpu-working` |
| **快照（snapshot）** | 保存某时刻磁盘（可选内存）状态；外部的会生成新 overlay | `winbox vm snapshot-save working` |
| **UEFI / OVMF** | 固件接口 / 开源的 UEFI 实现（虚拟机用） | `OVMF_CODE_4M.fd`（pflash） |
| **pflash / CODE 与 VARS** | UEFI 固件被当作两块 flash：只读的 CODE + 可写的变量区 VARS | `OVMF_CODE_4M.fd` + `OVMF_VARS_4M.fd` |
| **Secure Boot** | 固件校验启动链签名 | **关闭**（否则未签名的 GOP ROM/kvmfr 模块都不行） |
| **TPM / swtpm** | 可信平台模块 / 软件实现 | `tpm-crb` + `swtpm`（Win11 需要） |
| **设备模拟 vs 直通** | 模拟＝QEMU 假装一个设备；直通＝把真设备整块交给客机 | 磁盘/网卡是模拟，核显是直通 |

## 二、PCI、IOMMU 与直通

| 术语 | 一句话 | 在本项目里 |
|---|---|---|
| **PCI 设备 / 功能（function）** | 一个物理设备可含多个功能（同一个 slot 下的 .0/.1…） | 核显 `.0` = VGA，`.1` = HDMI 音频 |
| **BDF** | 设备地址 `域:总线:设备.功能` | `0000:0d:00.0` |
| **BAR** | Base Address Register：设备把自己的内存/IO 窗口声明给系统 | 核显 BAR0=显存窗口、BAR2=寄存器；IVSHMEM BAR2=共享内存 |
| **MMIO / PIO** | 用内存读写方式访问设备寄存器 / 用 IO 端口访问（老式） | legacy VGA 端口 `0x3b0-0x3df` 属 PIO |
| **legacy VGA 资源** | 老式显示设备的固定 IO 端口与内存窗口（`0xa0000-0xbffff`） | **两个 VGA 设备会抢它** → 所以 `x-vga` 与虚拟显卡互斥 |
| **IOMMU（AMD-Vi）** | 把设备 DMA 地址翻译/隔离，使直通安全可行 | 内核参数 `amd_iommu=on iommu=pt` |
| **IOMMU group** | 共享同一翻译域、必须一起直通的最小设备集合 | 核显 `.0/.1` 各成组 |
| **VFIO** | 内核的"把设备安全交给用户态（QEMU）"框架 | `vfio-pci` 驱动绑定核显 |
| **vfio-pci** | VFIO 的 PCI 驱动；设备被它绑住，宿主就不能用 | 我们的核显就绑在它上面 |
| **`driver_override`** | 强制某设备只能用指定驱动绑定 | 交接 vfio-pci ↔ amdgpu 时必用 |
| **unbind / bind / `drivers_probe`** | 解绑 / 绑定 / **显式触发一次探针** | 内核**不会**在 unbind 后自动重新匹配驱动 |
| **Option ROM / ROM BAR** | 设备固件区（PCI 有个 ROM BAR 把它映射出来） | VGA 挂 VBIOS，音频挂 GOP |
| **VBIOS / ATOM 表** | 显卡传统固件（含时钟、显存、显示模式等表） | `vbios_ref_9800x3d.bin` |
| **GOP（Graphics Output Protocol）** | UEFI 环境下的显示驱动接口（现代固件用它点屏） | `AMDGopDriver_9800x3d_plain.rom` 挂在音频功能上 |
| **PCIR 结构** | Option ROM 里描述"这镜像给哪个设备/哪种代码"的结构（vendor/device/class/codeType） | 我们核对过：VBIOS `1002:13c0` codeType=0；GOP codeType=3 |
| **FLR / 复位 bug** | Function Level Reset / AMD 显卡在被虚拟机用过之后难以真正复位 | 见 03 篇；解法是让宿主 `amdgpu` 做一次 **MODE2 reset** |
| **MODE2 reset** | AMD GPU 的一种复位方式（SMU 级），`amdgpu` 解绑时会做 | 钩子日志里的关键证据 |
| **Resizable BAR / Above 4G** | 让显卡把整段显存通过一个大 BAR 暴露 / 允许把大 BAR 放在 4G 以上 | 宿主 amdgpu 报 `BAR=2048M` |

## 三、显示栈相关（Windows 侧最关键的一节）

| 术语 | 一句话 | 在本项目里 |
|---|---|---|
| **POST（显卡）** | 开机时固件对显卡做初始化（设置显示模式、点亮输出） | 宿主机固件 POST 核显；客机里由 OVMF + 我们的 ROM 完成 |
| **启动/主显示设备** | 固件点亮、系统当作"启动显示"的那块 | 与 `x-vga`(Primary GPU) 相关 |
| **framebuffer / scanout** | 帧缓冲 / 扫描输出：GPU 把哪块内存当作"当前画面"往外送 | 05 篇里"被写坏的"就是这块 |
| **EDID** | 显示器上报的能力表（分辨率、时序） | 诱骗插头（dummy plug）就是伪造 EDID 让显卡以为接了显示器 |
| **显示适配器 / 显示器 / 输出** | Windows 里三个层级：适配器(GPU) → 输出(接口) → 显示器 | 我们有 2 个适配器：AMD 核显、LG IDD |
| **WDDM** | Windows 的显示驱动模型（显示驱动的框架规范） | AMD 核显驱动、LG 的 IDD 都遵循它 |
| **DWM** | Desktop Window Manager：Windows 桌面合成器，负责最终画面 | 它的输出就是我们看到的桌面 |
| **IddCx / IDD（间接显示驱动）** | 微软 WDDM 里允许**用户态驱动注册出一个"虚拟显示器"** 的框架 | LG IDD 用它凭空造出 "Looking Glass" 显示器 |
| **DXGI Desktop Duplication** | 抓取某个显示输出画面的官方 API（只读） | LG 传统 Host 应用用它（我们未用） |
| **硬件光标 vs 软件光标** | 光标是由 GPU 单独一块内存叠加，还是画进帧里 | 多显示器下 LG 的指针错位与光标瓦片问题相关 |
| **绝对定位 vs 相对定位（capture 模式）** | 鼠标事件带屏幕坐标 / 只带位移增量 | LG 绝对定位依赖"唯一显示器"假设，故我们改用 capture 模式 |
| **TDR** | Windows 检测到 GPU 长时间无响应就复位驱动（"显示驱动停止响应并已恢复"） | AMD 驱动在 IDD 的 HeapTest 上触发 `Device Removed` |
| **`DXGI_ERROR_DEVICE_REMOVED (0x887A0007)`** | GPU 已被移除/挂起，命令无法完成 | 05 篇的核心日志 |
| **代码 43 / 代码 10** | 设备管理器的问题码：43=驱动启动后自报问题；10=启动失败 | 代码 43 是我们解决的核心目标 |
| **`STATUS_GRAPHICS_NOT_POST_DEVICE_DRIVER (0xC01E0438)`** | 显示栈："驱动不是当初 POST 该设备的驱动" | 我们曾在 BasicDisplay 上遇到，属附带现象 |

## 四、共享内存、协议与"零拷贝"

| 术语 | 一句话 | 在本项目里 |
|---|---|---|
| **共享内存（IPC）** | 两个不同执行体（客机/宿主）看到同一段物理内存 | 整个 LG 通路的基础 |
| **IVSHMEM** | QEMU 的一个 PCI 设备：把一段宿主内存映射进客机 | `-device ivshmem-plain`，128MB |
| **ivshmem-plain / -doorbell** | IVSHMEM 的两种形态：纯内存 / 带中断通知 | 我们只用 plain |
| **设备接口 GUID** | Windows 里"某类驱动对外提供的可打开对象"的标识 | `{df576976-…}` = `GUID_DEVINTERFACE_IVSHMEM`（virtio-win 驱动提供） |
| **IOCTL** | 用户态↔内核驱动 的命令通道 | IDD 用 `IOCTL_IVSHMEM_REQUEST_MMAP` 拿到内存指针 |
| **mmap** | 把文件/设备映射成一段内存 | 宿主客户端 mmap `/dev/kvmfr0` |
| **缓存属性 WB/WC/UC** | 普通写回 / 写合并 / 不缓存；影响带宽与可见性 | IDD 取共享内存用 **WRITECOMBINED** |
| **DMA-BUF** | Linux 内核的跨设备缓冲区共享机制（可给出"能直接给 GPU 用"的句柄） | KVMFR 用它让宿主 GPU 零拷贝导入 |
| **KVMFR** | LG 自己的内核模块：既是 IVSHMEM 宿主后端，又能导出 DMA-BUF | `/dev/kvmfr0` |
| **LGMP** | Looking Glass Memory Protocol：共享内存上的无锁队列协议 | 帧队列/光标队列/输入队列/剪贴板都走它 |
| **KVMFR 头** | 共享内存开头的元信息区（magic/版本/能力位） | IDD 启动先写它，客户端用来校验与协商能力 |
| **direct / indirect（直写 vs 回读）** | GPU 直接把帧写进共享内存 / 先读到 CPU 再拷进共享内存 | AMD 驱动直写必挂 → 我们强制 indirect |
| **partial damage copy** | 只拷贝画面变化过的"脏矩形"（省带宽的优化） | indirect 模式下仍是脏区拷贝；与白方块相关 |
| **零拷贝（zero-copy）** | 数据不经过 CPU 复制，直接交给下一级（这里是宿主 GPU） | 客户端日志 `Using DMA buffer support` |

## 五、Looking Glass 架构术语

| 术语 | 说明 |
|---|---|
| **客户端（client）** | 跑在 Linux 宿主的程序：接收帧、显示、发送输入 |
| **服务端（server / host）** | 跑在 Windows 客机的程序：产生帧、注入输入。两种实现：**IDD**（推荐）与 **传统 Host 应用**（DXGI 抓屏） |
| **transport（传输）** | 客户端选择的主通道：`lgmp`（共享内存）或 `spice`（兜底） |
| **输入提供者** | 客户端日志里的 `Using Input: LGMP`（IDD 直连）或 `SPICE`（兜底，相对鼠标） |
| **IVSHMEM 尺寸公式** | `(宽按256B对齐 ×4B × 高) ×3 + 4MiB`，向上取 2 的幂；1080p=32MB、1440p=64MB、4K=128MB |
| **动态模式 / ExtraMode** | 客户端请求、IDD 动态创建的分辨率（`win:setGuestRes`） |
| **DefaultRefresh** | 请求动态分辨率时用的刷新率 |
| **frame schedule owner** | 帧调度：IDD 按"最快客户端请求的帧率"发帧，多余的直接跳过（省带宽） |
| **同版本要求** | 客户端 / IDD / OBS 插件共享内存协议，**必须同一 release** |

## 六、性能与延迟相关

| 术语 | 说明 |
|---|---|
| **topoext** | AMD CPU 的扩展拓扑 CPUID（暴露 SMT/缓存拓扑）；LG 明确建议给客机打开 |
| **SMT / 线程拓扑** | 一个物理核两个线程；客机拓扑与宿主不一致会影响延迟敏感任务 |
| **CPU pinning（vcpupin）** | 把 vCPU 钉在物理核上，减少调度抖动 |
| **memlock / `<locked/>`** | 把客机内存锁在 RAM，避免换页抖动 |
| **hugepages** | 大页内存，降低 TLB 缺失 |
| **IVSHMEM 容量** | 常驻占用宿主内存；超配不提升性能 |
| **`mouseRedraw`** | 客户端"仅光标变化时按显示节奏重绘"的优化开关（我们关掉过以规避光标问题） |

## 七、把术语串起来：从一次鼠标移动，到画面出现在宿主窗口

```
① 你在 LG 窗口里移动鼠标
② 客户端（Linux）把事件写进共享内存的「输入队列」（LGMP）
③ 客机里的 IDD 输入驱动从共享内存取事件 → 注入 Windows（相对位移，capture 模式）
④ DWM 合成桌面 → 更新 IDD 的虚拟显示器
⑤ LGIdd.sys 把"脏区"用 GPU 渲染/拷贝到本地资源，再（indirect）经 CPU 回读写进共享内存
   （帧数据 + 帧队列条目）
⑥ 宿主客户端读共享内存 → 经 KVMFR 的 DMA-BUF 把帧**零拷贝**导入 NVIDIA 纹理 → EGL 画到窗口
⑦ 同一轮里，光标形状走「光标队列」，剪贴板走剪贴板通道
```

其中：
- ②③ 属于 **输入通路**（不经 QEMU 的模拟键鼠）；
- ④⑤⑥ 属于 **视频通路**（不经 QEMU 的显示栈、不经编码）；
- **共享内存（IVSHMEM/KVMFR）是这两条通路的交汇点**，也是本方案绕开 SPICE/VNC 的关键。

## 九、这些项目的来源与历史（谁为谁做的）

| 组件 | 出身 | 是不是为 LG 做的 |
|---|---|---|
| **IVSHMEM** | **QEMU，2010-03**，Cam Macdonell 的 *"Inter-VM shared memory PCI device"* 补丁 | ❌ 通用设施（比 LG 早 7 年）：面向 VM↔VM / VM↔宿主 的共享内存通信，带 peer ID 与 doorbell 中断。QEMU 2.6（2016）拆成 `ivshmem-plain` / `ivshmem-doorbell` |
| **ivshmem 的 Windows 驱动** | 谱系来自 Virtual Open Systems 的 IVSHMEM/PCI-SHM 驱动 → 现由 **virtio-win** 维护（`kvm-guest-drivers-windows/ivshmem`） | ❌ 通用：它就是"那个 PCI 设备的 Windows 驱动"。INF 里匹配 `PCI\VEN_1AF4&DEV_1110`，并注册设备接口 `{df576976-569d-4672-95a0-f57e4ea0b210}`（= `GUID_DEVINTERFACE_IVSHMEM`） |
| **KVMFR** | **Looking Glass 项目自己**的（`Copyright © 2017-2026 The Looking Glass Authors`） | ✅ **专为 LG**：官方文档原话 *"The kernel module implements a basic interface to the IVSHMEM device for Looking Glass allowing DMA GPU transfers."* 动机是 QEMU 的 IVSHMEM / 普通共享文件**无法导出 DMA-BUF** → 客户端必须再拷一遍 ✗；KVMFR 同时充当"IVSHMEM 宿主后端"与"DMA-BUF 导出者" |
| **LG 本体 / LGMP / IDD / 客户端 / PureSpice** | gnif（Geoffrey McRae）等，版权自 2017 起 | ✅ 项目本身。其中 LGMP、LGProtocol、PureSpice 是从项目里拆出的自有库 |
| **IddCx** | 微软（WDDM 的一部分） | ❌ 通用框架，LG 的 IDD 只是它的实现者 |
| **SPICE** | Red Hat | ❌ 通用；LG 用它做音频/剪贴板/兜底输入（还自己写了 PureSpice 客户端） |
| **DMA-BUF** | Linux 内核（2011 起） | ❌ 通用机制 |
| **QEMU / libvirt / OVMF / virtio-win** | 各自社区 | ❌ 通用基建 |

**一句话**：LG 文档里那条路整体叫 "IVSHMEM"，但它是三件来源不同的东西拼起来的 ——

```
QEMU 的 ivshmem-plain 设备（2010，通用）
   + virtio-win 的 ivshmem.sys（通用 Windows 驱动）   ← IDD 通过它的设备接口 + IOCTL 拿到内存指针
   + LG 的 KVMFR（LG 专用：宿主后端 + DMA-BUF 能力）
   + LG 的 LGMP / IDD / 客户端（LG 本身）
```

这也解释了 LG 文档里两个并列选项的命名逻辑：
**"IVSHMEM with KVMFR module"** 与 **"IVSHMEM with standard shared memory"** —— 都是 IVSHMEM，
区别只在**宿主侧后端**是不是带 DMA-BUF 能力的 KVMFR。
