# 07 踩坑大全（症状 → 原因 → 修法）

> 本文按"遇到时的顺序"记录，每条都是实际卡住过一轮以上的。

## 宿主 / 虚拟化层

> **关于本文**：这是当时的**实录**（含走过的弯路与证据），不是使用说明。
> 命令已规整为本仓库的形式（`winbox …`）；接口以 `docs/interfaces/` 为准。

### 坑 1：`blacklist amdgpu` 管不住 initramfs

**症状**：initramfs 里始终有 `amdgpu.ko` + 663 个 amdgpu 固件（镜像 212MB），
宿主启动时 amdgpu 仍然被加载。
**原因**：`blacklist` 只影响**按 alias 自动加载**；`/etc/initramfs-tools/modules` 里的条目是**显式 modprobe**，不受 blacklist 约束。
**修法**：把 `amdgpu` 从 `/etc/initramfs-tools/modules` 删掉 → initramfs 条目 663→0，体积 212MB→178MB。

### 坑 2：内核 7.0 的 vfio-pci 参数疑云

**症状**：怀疑 `options vfio-pci ids=…` 在新内核失效。
**结论**：**仍然有效**。journal 里有 `vfio_pci: add [1002:13c0[ffffffff:ffffffff]]` 为证。
（`/sys/module/vfio_pci/parameters/` 列表里看不到 `ids` 只是因为该参数在加载后不再暴露；
`modinfo` 里仍在。）→ 判断这类问题**看 journal，不看 sysfs**。

### 坑 3：QEMU 打不开 `/dev/kvmfr0`（两种"Permission denied"）

**症状 A**：`qemu-system-x86_64: can't open backing store /dev/kvmfr0 for guest RAM: Permission denied`
**原因 A**：AppArmor。`abstractions/libvirt-qemu` 白名单里有 `/dev/kvm`、`/dev/vfio/vfio`、`/dev/vhost-net`，**没有 `/dev/kvmfr0`**。
**修法 A**：`/etc/apparmor.d/local/abstractions/libvirt-qemu` 追加 `/dev/kvmfr0 rw,`。

**症状 B**：修完 A 仍失败（或报 EPERM）。
**原因 B**：libvirt 在 cgroup v2 下用 eBPF 做**设备白名单**，白名单 = `qemu.conf` 的 `cgroup_device_acl` + XML 中登记过的设备。
用 `qemu:commandline` 裸参数加的设备，libvirt 并不知情。
**修法 B**：在 `/etc/libvirt/qemu.conf` 写明 `cgroup_device_acl = [ …默认项…, "/dev/kvmfr0" ]` 并重启 libvirtd。
→ 诊断技巧：**EACCES 多为 AppArmor/DAC；EPERM 多为 cgroup eBPF**。

### 坑 4：QEMU 把 `/dev/kvmfr0` 创造成普通文件

**症状**：之后 `modprobe kvmfr` 也建不出字符设备，LG 客户端连不上。
**原因**：VM 先启动、模块未加载，QEMU 用 `memory-backend-file` 打开不存在的路径时会**创建普通文件**。
**修法**：先 `modprobe kvmfr`（已配开机自动加载）；已中招则：关 VM → `rm -f /dev/kvmfr0` → `modprobe kvmfr` → 确认 `c` 开头 → 再启动 VM。

### 坑 5：`x-vga=on` 与任何虚拟显卡互斥

**症状**：加了 QXL 后核显代码 43，物理屏停在固件画面。
**原因**：两个 VGA 设备抢 legacy VGA 资源（`0x3b0-0x3df`、`0xa0000-0xbffff`）；mtree 里可见两套区域。
**修法**：`<video><model type='none'/></video>`（这也解释了 Proxmox 的 "Primary GPU 需要 vga: none"）。

### 坑 6：`driver_override` 工作流有两个必备动作

**症状**：想换驱动绑定（vfio-pci ↔ amdgpu），unbind 后设备一直"无驱动"，日志里连 probe 记录都没有。
**原因 1**：`options vfio-pci ids=…` 注册的动态 ID 会让 vfio-pci 在解绑瞬间抢回设备。
**原因 2**：`unbind` 后内核**不会自动重新匹配驱动**。
**修法**：
```bash
echo <目标驱动> > /sys/bus/pci/devices/<dev>/driver_override   # 先指明目标
echo <dev> > /sys/bus/pci/devices/<dev>/driver/unbind
echo <dev> > /sys/bus/pci/drivers_probe                        # 必须显式触发 probe
```
（还有一个低级但致命的点：**unbind 文件里要写设备名**，写成驱动名会得到 `No such device`。）

### 坑 7：`virsh destroy` 会毁 NTFS

**症状**：强制断电后客机进不去系统，`ACPI.sys` 报 `0xc0000102`；`chkdsk` 才修好。
**修法**：**永远用 ACPI 关机**（`virsh shutdown`，等它自己关完）；救急前先拍快照。

## Looking Glass 层

### 坑 8：客户端配置里 `shmDevice=` 留空会段错误

**症状**：客户端启动即 `FATAL CRASH … signal 11`，栈顶在 `lgmp_deviceValidator`。
**原因**：空值让校验器对 NULL 调 `strlen`。
**修法**：显式写 `shmDevice=/dev/kvmfr0`。

### 坑 9：`win:autoResize` 与 `win:setGuestRes` 互斥

**症状**：启动时警告 `win:autoResize (-a) and win:setGuestRes can't be used simultaneously`。
**修法**：二选一。我们保留 `setGuestRes=yes`（窗口决定客机分辨率），`autoResize=no`。

### 坑 10：LG 剪贴板需要客机装 `spice-vdagent` 吗？

**结论**：用 **IDD** 时不需要 —— 剪贴板走 LGMP（日志 `Using Clipboard: LGMP`）。
但我们踩过另一种：IDD 的**剪贴板权威在反复注册/清除**（日志每秒一对 `Register/ ClearClipboardAuthority`），
表现为宿主→客机粘贴永远不生效。重载 IDD 设备后恢复正常（`Clipboard owner N generation M acquired`）。

### 坑 11：`ideo`「Make LG the only monitor」是默认开启的

**症状**：装了 IDD 后物理屏被"主动关掉"，看起来像"两屏不能共存"。
**原因**：IDD 助手默认策略 *ExclusiveMonitor=1* 会强制 LG 成为唯一活动显示器。
**修法**：`HKLM\SOFTWARE\LookingGlass\IDD` → `ExclusiveMonitor=0`（见 02/05 篇）。

### 坑 12：多显示器下 LG 的绝对定位会把指针送到别的屏

**症状**：鼠标移入 LG 窗口 → 指针出现在**物理屏**上；随之物理屏出现网格白方块。
**原因**（源码级）：绝对定位最终调用 `SetCursorPos(x,y)`（**桌面绝对坐标**），
而该设计前提正是"LG 是唯一显示器"；扩展桌面下客户端视口坐标被当作桌面坐标使用。
**修法**：客户端配置用**抓取模式**（相对位移 + 指针锁在视图内）：
```ini
[input]
captureOnFocus=yes
grabKeyboard=yes
mouseRedraw=no
```
取舍：指针不能离开 LG 视图；窗口跨屏用 `Win+Shift+方向键`；临时要用物理屏按 `ScrLk` 释放。

## 客机 / 工具层

### 坑 13：Windows Defender 拦"下载即执行"

**症状**：`cmd /c "curl … & %TEMP%\x.bat"` 或 `iex(iwr …)` 被拦，连下载都没发生（服务端无请求日志）。
**修法**：拆成两步（先下载、后执行），且避免脚本内容里带自提权（`Start-Process -Verb RunAs`）——
那会被判为可疑。更彻底的做法是**改用 SSH**（见 04 篇）。

### 坑 14：Win+R 的自动补全毁掉长命令

**症状**：注入按键控制客机时，长命令经常不执行；短命令却正常。
**原因**：Run 对话框会自动补全历史命令（首词匹配），把后续输入搅乱。
**修法**：优先用短命令；或改用 `cmd` 窗口内执行；或（最好）用 SSH。

### 坑 15：SSH 会话看不见真实桌面/剪贴板

**症状**：`[System.Windows.Forms.Screen]::AllScreens` 返回 `WinDisc 1024x768`，
`Get-Clipboard` 拿不到用户剪贴板。
**原因**：SSH 是**非交互会话**，与登录会话（session 1）隔离；那些 API 属于登录会话。
**修法**：查显示器拓扑/剪贴板要在客机内的登录会话里做（或看 IDD 日志、注册表配置）。

### 坑 16：日志编码

**症状**：用 `wevtutil`/cmd 重定向采集的日志，回传后中文全成乱码（"锟斤拷"），不可恢复。
**原因**：控制台代码页（GBK）与 UTF-8 多重转码，且已经用替换字符丢掉信息。
**修法**：采集脚本开头 `chcp 65001`；或经 SSH 用 PowerShell 并设置
`[Console]::OutputEncoding=[System.Text.Encoding]::UTF8`。

### 坑 17：unbind 之后设备被"动态 ID"抢回（把核显交回宿主最坑的一处）

**症状**：把核显还给宿主：清了 `driver_override`、从 vfio-pci 解绑、`modprobe amdgpu` 也成功
（`lsmod` 里 amdgpu 在位、绑定数 0），但设备**又回到 vfio-pci**；日志里只有 vfio-pci 的
`vgaarb` 行，看不出谁抢的。

**原因**：`options vfio-pci ids=…` 是在**模块加载时**注册成"动态 ID"的，注册后一直有效，
直到模块卸载或显式 `remove_id`。所以"删配置 + unbind"并不等于设备自由了 ——
只要发生一次 probe/uevent，vfio-pci 就凭旧动态 ID 把它抢回去。

**修法**（顺序很重要）：

```bash
echo "1002 13c0" > /sys/bus/pci/drivers/vfio-pci/remove_id   # ① 先清动态 ID
echo "1002 1640" > /sys/bus/pci/drivers/vfio-pci/remove_id
echo 0000:0d:00.0 > /sys/bus/pci/drivers/vfio-pci/unbind    # ② 解绑
modprobe amdgpu                                             # ③ 先加载目标驱动
echo 0000:0d:00.0 > /sys/bus/pci/drivers/amdgpu/bind        # ④ 再**显式**绑定
```

三个附带的教训：
* **别用 `drivers_probe` 代替显式 bind**：`probe` 是"让所有驱动来匹配"，在动态 ID 还在时
  等于把设备直接送给 vfio-pci；
* **音频功能（`0d:00.1`）的目标驱动是 `snd_hda_intel`，不是 amdgpu** —— 它是 HDMI 音频控制器；
* **刚 unbind 后立刻 bind 可能瞬时失败**：unbind amdgpu 会触发 MODE2 reset，设备事后处于瞬时
  状态。实测同一台机器上"第一次 bind 失败、几分钟后重试成功"（日志里能看到
  `amdgpu … finishing device.` + `MODE2 reset` 紧跟着一次失败的 bind）。**绑定要带重试**。

还有一个写脚本时的坑：`wb_pci_bind "$d" vfio-pci || true` **拦不住失败** —— 如果那个函数内部
用的是 `exit`（我们原来就是 `wb_fail`），`|| true` 只对"返回码"有效，于是"尽力而为"的循环会在
第一个失败处**整体中断**：后面的设备没处理、期望状态没落盘、设备被留在无驱动状态。
正确做法是提供"返回失败而不退出"的软变体，并让循环继续跑完再统一汇报。

### 坑 18：sysfs 里看不到的参数 ≠ 参数无效

**症状**：`ls /sys/module/vfio_pci/parameters/` 里**没有 `ids`**，于是判定"新内核移除了 ids=
参数、`options vfio-pci ids=` 一直是空转"，差点据此改掉整套配置。

**真相**：参数存在，只是**权限位为 0**，因此 sysfs 不生成该文件（同款坑还有 kvmfr 的
`static_size_mb`）。判据要看两处：

```bash
modinfo -p vfio-pci | grep '^ids'     # 参数存在且格式说明 —— 这才是权威
journalctl -b | grep 'vfio_pci: add'  # 运行期证据：动态 ID 真的注册了
```

**教训**：`/sys/module/*/parameters/` 是"可读写参数的视图"，不是参数清单。
判断"某个模块参数是否有效"必须用 `modinfo -p` + 运行期日志，而不是看目录列表。
